## A. Money-logic bugs

### A1 — A mis-keyed payment can never be corrected, and permanently inflates the doctor's commission ⚠️ highest
`deletePayment` (`lib/mutations.ts:303`) exists and is tested, but **has zero callers** — no
screen can edit or delete a payment. The only correction path is a `refund`, and
`computeSettlement` excludes `kind='refund'` from the doctor's collected total
(`lib/settlement.ts:68`).

Concretely: reception types `500,000` instead of `50,000`.
- Refund `450,000` → cash on hand ✅, patient balance ✅
- Doctor's commissionable base stays **500,000 forever** ❌

**Fix (pick one):** expose a void/delete action over the existing mutation, **or** make refunds
net against the doctor's collected total. Probably both.

### A2 — Refunds are excluded from commission by design [D5]
Same root as A1. `scripts/verify.ts:105` asserts this as *correct* ("refund excluded [D5]").
Financially, the doctor is paid a percentage of money the clinic handed back. This is a clinic
decision, not a code decision — it belongs in the Layer-2 "غير مؤكد" list, not silently baked in.

### A3 — The implant card edit silently breaks `total = listPrice − discount`
`lib/actions/implants.ts:107-115` writes `totalPrice` and `discount` but **never `listPrice`**,
and nothing recomputes the total. Editing «الخصم» from 0 → 500,000 stores the number and
**changes nothing about الإجمالي**. The user believes a discount was applied.

**Fix:** recompute `totalPrice = listPrice − discount` server-side, or make discount read-only
in the edit dialog.

### A4 — Completed cases with a balance sit on the call-list but can't be paid
`debtsList` includes `completed` (`lib/queries.ts:199`: `status != 'cancelled'`), but
`recordCasePayment` rejects any non-open case (`lib/mutations.ts:281`). Pressing «تسجيل دفعة»
on such a row **always** fails with «لا يمكن تسجيل دفعة على حالة غير مفتوحة».
Reachable today via the implant card status dropdown.

**Fix:** allow collection on `completed` (the money is still owed) or drop them from the list.

### A5 — Clearing a % box on close silently books 0%
`lib/actions/settlement.ts:36`: `Number("")` is `0` and `Number.isFinite(0)` is `true`, so an
empty field becomes `overrides[id] = 0` instead of falling back to the doctor's %.
`normalizeCommissionPct`'s `fallback` argument (`lib/settlement-math.ts:22`) is dead for the
same reason. The live preview also shows 0, so it is visible — but one blank box freezes a
doctor's month at zero.

**Fix:** `if (String(value).trim() === "") continue;` in `closeMonth`; guard
`normalizeCommissionPct` on the raw string, not the coerced number.

### A6 — Negative payouts have nowhere to go
Lab cost is booked in the month the case **opens** (`lib/settlement.ts:86-91`), while the money
arrives over later months. The moment the clinic turns on «خصم المختبر من الطبيب» — the entire
point of that Layer-2 switch — `calculateDoctorPayout` can go negative. `closeSettlement`
snapshots the negative, `finalizeSettlementPayout` then refuses it (`non_positive`), and the
negative silently **inflates** `clinicNet`. There is no carry-forward / doctor-owes-clinic concept.

### A7 — Dashboard numbers don't reconcile
`lib/queries.ts:279` («تحصيل هذا الشهر») nets refunds; `lib/queries.ts:291` (per-doctor table)
excludes them. With any refund in the month, the per-doctor rows sum to **more** than the
headline. Small, but this is exactly the mismatch that makes an accountant distrust the system.

## B. Registers from the brief that aren't built

### B1 — السجل الرئيسي (appointments): table exists, nothing uses it
`appointments` (`lib/db/schema.ts:147`), its migration, and `APPT_STATUS_LABELS`
(`lib/strings.ts:51`) have **zero references** in `app/`, `lib/queries.ts`, `lib/mutations.ts`.

This is register **#1** in `BRIEF.md` — *"اسم المراجع وعلياته بيجاي"* — and the entire subject of
`IMG_5711`. `BRIEF.md` puts it in **Layer 1** ("build fully now"). Ortho has a `nextAppointment`
field, but there is no day view, no booking, no «جاي / ما جاي». Zahra's 2-days-a-week ortho
schedule has nowhere to live.

### B2 — The 5-million cash rule has a banner but no mechanism
`recordCashMovement` (`lib/mutations.ts:352`) has **zero callers**; `CASH_MOVE_LABELS` is unused.
The dashboard shows the amber over-threshold banner, but there is no way to record a reserve, a
withdrawal, or an owner draw. Only settlement payouts ever write to `cash_movements`.

### B3 — No audit-log screen
The audit table is written on every mutation and is the stated replacement for the كبير/صغير
dual ledger (*"the big one must have zero errors"*, the doctor reviews it). **Nothing in `app/`
reads it.** No way to see who changed what, or to review the `hitClosedPeriod` flagged edits.

### B4 — Staff salaries
`staffSalaryMode` is a free-text input that nothing reads; `clinicNet` is computed with
salaries = 0. Known Layer 2 — but right now the field is purely decorative.

### B5 — No doctor management
Settings edits only the commission %. No add / rename / deactivate, even though `updateDoctor`
already supports `isActive` and `doesOrtho`. Adding a doctor means editing `seed.ts`.

## C. Spec violation vs CLAUDE.md / BRIEF

### C1 — Commission % is hardcoded in the seed, so «غير مؤكد» never shows
`lib/db/seed.ts:13-17` seeds Adi = 100%, everyone else = 50%. The settings badge only renders
when `commissionPct == null` (`settings-forms.tsx:247`). `BRIEF.md` lists commission % under
**STILL UNKNOWN**, and `CLAUDE.md` golden rule 4 says never hardcode Layer 2 numbers.
Result: every doctor's percentage currently looks confirmed. (The settlement page's global
banner partly covers this.)

**Fix:** seed `commissionPct: null` and let `defaultCommissionPct` fill in, so every doctor
carries the badge until the clinic confirms.

## E. Deployment / operational risk

### E1 — `next start` listens on all interfaces, and the PIN has no rate limit
`README.md` says `npm start` with no `-H 127.0.0.1`, so anyone on the clinic wifi can reach the
app. `loginAction` has no throttling or lockout against a 4-digit PIN (10,000 combinations).
**Fix:** `"start": "next start -H 127.0.0.1"` + attempt throttling.

### E2 — Mistyping the new PIN locks the clinic out permanently
`changePin` has no confirm field, and there is no reset path — `db:seed` will not reset an
existing `pinHash`. Recovery means hand-editing SQLite.
**Fix:** confirm field + `npm run pin:reset` + document it in the handover.

### E3 — `next/font/google` needs internet at build time
`app/layout.tsx:6` fetches Cairo from Google during `next build`. The whole premise is an
offline on-prem laptop; a rebuild without internet fails. **Self-host the font file.**

### E4 — Backups live next to the database
`backups/` is inside the project folder on the same disk. Laptop dies = the clinic's entire
financial history dies. The handover needs a USB / network copy step.

### E5 — No version control
No `.git` in the project. `.gitignore` correctly excludes the DB and backups, but nothing is
tracked.

### E6 — Nothing was run this pass
`node_modules` stripped, disk at 93%. `npm test`, `npm run typecheck` and `scripts/verify.ts`
all need a re-run. `verify.ts` is also not wired into `package.json` scripts.

## What's genuinely solid

- The **mutation layer is well-guarded**: credited doctor derived server-side never from form
  input, overpayment and refund ceilings, `expectedCourse` guards, atomic transactions where an
  audit failure rolls the payment back, integer dinars throughout. 13 real tests cover the
  invariants.
- `requireAuth()` on **every** server action (not just the layout), scrypt-hashed PIN,
  HMAC-signed session, secret columns kept out of the RSC payload.
- The closed-period staleness mechanism (D4) is a genuinely good answer to the كبير/صغير
  duplication problem.
- Every register in the brief **except appointments** has a working screen, and the Layer-1 /
  Layer-2 split held up.

### Architectural risks — need the clinic's explicit sign-off (not code defects)

1. **`zuha.db` is unencrypted.** Anyone with physical access to the laptop can read every
   patient record and every number. Inherent to on-prem; the paper ledgers it replaces had the
   same property. Mitigation if wanted: full-disk encryption on the clinic laptop.
2. **One shared PIN → no per-user attribution.** The audit log records *what* changed, never
   *who*. This was the clinic's own choice (BRIEF: "~4 users, ONE shared PIN"). Per-user
   accounts would be needed for attribution.
3. **`npm run pin:reset` resets access from the machine.** That is the intended recovery path
   and requires physical access — the same boundary as #1.

**Status: 9 PASS · 2 N.A. · 0 FAIL.** Not "ALL PASS — safe to ship" until the three risks
above are explicitly accepted by you/the clinic, since they are decisions rather than bugs.
